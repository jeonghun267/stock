# ② 유령 주문 창

## 정체 — `+5` 한 줄이다

`broker_client.py:207`

```python
req.setdefault("ttl_sec", int(timeout_sec) + 5)
```

`send_order_real` 의 기본값이 `timeout_sec = 10.0`(435줄) →

```
클라이언트 : 10초 기다리고 포기 → 호출부는 TIMEOUT 처리
게이트웨이 : 15초까지 유효로 보고 실행
             ↑ 이 5초 안에 실행되면 아무도 모르는 주문이 나간다
```

**종가매수도 같은 창에 있다.** `eod_gap_live_executor_v1.py:235` 가 `timeout_sec` 를 안 넘겨서 기본 10초를 쓴다.
게다가 매수는 `TIMEOUT` 을 성공으로 기록한다(241줄 `_ok = _st in ("OK","TIMEOUT")`) → **유령이 곧바로 OPEN 포지션이 된다.** ③과 같은 뿌리.

## 왜 `ttl = timeout` 으로는 부족한가

`ttl == timeout` 으로 맞춰도, 게이트웨이가 9.99초에 검사를 통과한 뒤 SendOrder를 부르는 그 사이에 클라이언트가 10.0초로 포기한다.
→ **여백이 필요하다.**

## 설계 — 양쪽에서 조인다

**클라이언트 쪽** (`broker_client.py` `send_order_real` 안, 요청 payload 조립부)

```python
            # [GHOST-WIN 2026-07-30] 실주문만 유예를 줄인다.
            #   클라가 timeout_sec 에 포기하는데 게이트웨이가 +5초 더 실행하던 창을 없앤다.
            #   TR·BATCH_TR 은 종전대로(낡은 조회는 무해하지만 낡은 주문은 위험).
            "ttl_sec": max(1, int(timeout_sec) - _GHOST_MARGIN_SEC),
```

**게이트웨이 쪽** (`_handle_sendorder_real_request` 맨 앞)

클라이언트가 이상한 값을 줘도 게이트웨이가 스스로 자른다.

```python
        # [GHOST-WIN 2026-07-30] 주문 유예 상한 — 클라 값이 더 커도 이 값으로 자른다
        _eff_ttl = min(int(req.get("ttl_sec", 15)), _order_cap_env("BROKER_ORDER_MAX_TTL_SEC", 8))
        _age = (datetime.now() - datetime.fromisoformat(str(req.get("ts","")))).total_seconds()
        if _age > _eff_ttl:
            if _GHOST_SHADOW:          # 그림자 모드 — 로그만
                logger.warning("[GHOST-SHADOW] 실거부였으면 차단됐을 주문 age=%.2fs > %ds code=%s",
                               _age, _eff_ttl, code)
            else:
                logger.critical("[GHOST-BLOCK] 늦은 주문 거부 age=%.2fs > %ds code=%s", _age, _eff_ttl, code)
                self._write_response(request_id, status="ERROR",
                    error=f"ORDER_TTL: 접수 지연 {_age:.2f}s > {_eff_ttl}s")
                return
```

| env | 기본 | 뜻 |
|---|---|---|
| `BROKER_GHOST_SHADOW` | `YES` | **오늘 밤은 YES(그림자)**. 7/31 데이터 보고 `NO` 로 |
| `BROKER_ORDER_MAX_TTL_SEC` | `8` | 클라 10초 대기 - 2초 여백 |

## 두 선택지 중 왜 (b)인가

원래 안 (a)=클라가 15초까지 기다림 / (b)=게이트웨이 유예 제거.

**(b)를 고른 이유: 놓치는 게 유령보다 낫다.**
거부된 매수는 기회 손실 1건이지만, 유령 매수는 원치 않는 포지션 + 슬롯 점유 + 다음날 매도 거부 반복이다.
(a)는 개장 러시 때 슬롯당 최대 5초를 더 잡아먹어 6슬롯 선착순 구조에 직접 손해다.

# ③ 종가매수 체결확인

## 지금 무슨 일이 일어나나

```
15:18  _buy_one → _order(...)   send_order_real(timeout 10초)
       status=OK      = SendOrder 접수 성공.  ★체결 아님
       status=TIMEOUT = 응답 못 받음
       둘 다 → held[code]="OPEN" + RT_OPEN 기록      (240~241줄)

익일 09:01  매도 시도 → 실제로 없는 주식이라 거부
            매도는 OK만 완료 처리 → OPEN 유지 → 다음날 또 거부
            = 슬롯 영구 점유
```

`status=OK` 는 `SendOrder ret=0`, 즉 **접수만** 뜻한다(`broker_client.py:457` 계약에 명시).
상한가는 정규장 호가가 0이라 미체결 가능성이 특히 높다 — 오늘 15:18 실전이 그 첫 사례다.

## 설계 — 에러 문자열을 추측하지 않는다

원래 계획은 "매도 거부 사유 문자열로 유령 판정"이었는데, **더 확실한 방법이 있다.**

> **15:31 에 잔고를 직접 조회해서 대조한다.**

`BALANCE_TR_WHITELIST` 에 `opw00018`(계좌평가잔고내역)이 이미 있다(`broker_gateway_v1.py:1341`).
읽기 전용이고 게이트웨이가 이미 허용한다. **추측 문자열이 필요 없다.**

```
15:30  장 마감(동시호가 종료)
15:31  opw00018 조회 → 실제 보유 종목·수량
       POS(eod_gap_positions.json) 의 status=OPEN 전부와 대조

       보유O + 수량일치  → 그대로 OPEN (정상)
       보유O + 수량부족  → qty 를 실제 보유수량으로 정정 (부분체결)
       보유X            → 유령. status="GHOST" 로 바꾸고 RT_OPEN 에서 제거
```

## 왜 15:31인가

동시호가는 15:30에 끝난다. 그 뒤라야 당일 매수분이 잔고에 확정으로 잡힌다.
15:18 주문 직후에 조회하면 아직 미체결 상태라 전부 유령으로 오판한다.

## 손대는 곳

- 새 파일 하나: `eod_gap_fill_check_v1.py` (읽기 + POS/RT_OPEN 정리만)
- 새 태스크 하나: `SAFEPLUS_EOD_GAP_FILLCHECK` 15:31 월~금
- **`eod_gap_live_executor_v1.py` 는 안 건드린다** — 매수 경로에 손대면 오늘 검증한 상한가 경로가 흔들린다

## 안전장치

- **읽기 + 정리만.** 주문을 내지 않는다
- 잔고 조회 실패 시 **아무것도 안 바꾼다**(fail-safe). 조회 실패로 멀쩡한 포지션을 지우면 더 큰 사고
- `GHOST` 로 바꾼 건 로그에 종목·수량·사유를 남긴다
- 첫날은 **판정만 하고 파일은 안 고치는 그림자 모드**로 돌려 대조 결과를 눈으로 확인 후 실동작 전환 권장

## 오늘 15:18 실전에서 확보할 재료

1. 상한가 주문의 `status` 가 OK 인지 TIMEOUT 인지
2. 15:31 잔고에 그 종목이 실제로 잡히는지 (= 동시호가 체결 여부, 별도 약속과 같은 재료)
3. 익일 09:01 매도 거부 시 에러 문자열 (보조 확인용·판정에는 안 씀)
