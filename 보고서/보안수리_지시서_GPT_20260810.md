# 작업 A — BATCH_TR 폴당 누적 상한 (🔴 이것이 본 지시서의 핵심)

## A-1. 무엇이 문제인가

8/7에 넣은 상한은 **요청 1건 기준**이다.

```python
BATCH_TR_MAX_CODES     = 50      # broker_gateway_v1.py:2598
BATCH_TR_MAX_BATCH_SEC = 120.0   # :2599
BATCH_TR_MAX_PER_REQ_SEC = 15.0  # :2600
```

그런데 브로커는 **한 번 훑을 때(poll) 발견한 요청 파일을 전부 순서대로 처리**한다.

```python
# broker_gateway_v1.py:3150~3187  poll_requests()
files = sorted(IPC_REQ.glob("*.json"))
...
for f in files:
    ...
    self.process_request(f)      # ← 발견한 것을 전부, 순차로
```

즉 BATCH_TR 요청 파일 100개가 한 폴에 잡히면 **100 × 120초 = 3시간 20분** 동안 브로커가 붙잡힌다.
그동안 **매도 주문(SENDORDER_REAL)이 큐에서 대기**한다. **손절이 안 나간다.**

## A-2. 이것이 "공격"이 아니라 "사고"로 터지는 이유 ← 우선순위의 근거

이 시스템은 재시도 로직을 여러 곳에 갖고 있고, 8/10에 엔진이 3개 죽었다.
수집기가 재시도 폭주하거나 응답 파일이 사라지면 **아무도 공격하지 않아도** 요청이 여러 개 쌓인다.
그리고 그때 브로커는 살아 있고 하트비트도 정상이라 **워치독이 절대 못 잡는다.**

## A-3. 왜 "폴당 상한"이 안전한가 — 정상 경로를 안 건드리는 근거

**정당한 호출자는 폴 하나에 BATCH_TR을 2개 이상 쌓을 수 없다.**

1. `broker_client.batch_tr()` 는 마지막 줄이 `return self.request(payload, timeout_sec=client_timeout_sec)`
   = **응답을 기다리는 동기 호출** (`RUN\broker_client.py:340`)
2. 유일한 사용처인 1분봉 수집기는 chunk 를 **순차 루프**로 보낸다
   (`RUN\collect_prices_1m_kiwoom_opt10080_v4_16.py:3063~3087`)
   `CHUNK_SIZE = 15` · `per_request_timeout_sec=5.0` · `batch_timeout_sec=30.0`

→ 정상 동작에서 **폴당 BATCH_TR = 1건**. 상한을 2로 잡아도 정상 경로는 절대 안 걸린다.

## A-4. 고칠 내용 (4곳)

### (a) 상수 2개 추가

`BATCH_TR_MAX_PER_REQ_SEC = 15.0` **바로 아래**에 추가:

```python
    # ★[SEC-BATCHTR-POLLCAP 2026-08-10] 요청 1건 상한은 폴 단위로 누적되지 않았다.
    #   poll_requests 는 한 번에 발견한 요청을 전부 순차 처리하므로
    #   요청 N개 = N×120초 브로커 점유 = 그동안 매도 주문이 큐에서 대기한다.
    #   브로커는 살아 있고 하트비트도 정상이라 워치독이 못 잡는다.
    #   정당 호출자는 응답을 기다리는 동기 호출이라 폴당 1건이 최대다(2배 여유를 둔다).
    #   근거: broker_client.batch_tr -> self.request() 블로킹(:340),
    #        수집기 chunk 순차 루프(collect_prices_1m_kiwoom_opt10080_v4_16.py:3063~3087)
    BATCH_TR_MAX_PER_POLL = 2
    BATCH_TR_MAX_POLL_SEC = 120.0
```

### (b) 폴 시작 때 초기화

`poll_requests()` 안에서 `files = sorted(IPC_REQ.glob("*.json"))` **바로 앞**에 추가:

```python

            self._batch_tr_poll_count = 0

```

> ⚠️ **위치 주의**: `poll_requests()` **안**이다(`self._poll_in_progress = True` 다음의 `try:` 블록 안).
> `run()` 의 메인 루프에 넣으면 안 된다.

### (c) 관문

`_handle_batch_tr_request()` 안에서
`if len(codes) > self.BATCH_TR_MAX_CODES:` **바로 앞**에 추가:

```python
        # ★[SEC-BATCHTR-POLLCAP 2026-08-10] 폴 단위 누적 상한.
        #   부등호는 뒤집어 쓴다 — `if x > MAX` 는 NaN 에서 거짓이라 그냥 지나간다(8/7 규칙).
        #   조용히 자르지 않고 거부한다 — 부분 결과는 정상으로 보여서 더 위험하다.
        _pc = getattr(self, "_batch_tr_poll_count", 0)
        _ps = getattr(self, "_batch_tr_poll_sec", 0.0)
        if not (_pc < self.BATCH_TR_MAX_PER_POLL) or not (_ps <= self.BATCH_TR_MAX_POLL_SEC):
            logger.error(
                "[SEC-BATCHTR-POLLCAP] rejected request_id=%s poll_count=%d poll_sec=%.1f caller=%s",
                request_id, _pc, _ps, str(req.get("caller") or "")[:40])
            self._write_response(request_id, status="ERROR",
                error=(f"BATCH_TR: poll budget exhausted "
                       f"(count={_pc}/{self.BATCH_TR_MAX_PER_POLL}, "
                       f"sec={_ps:.1f}/{self.BATCH_TR_MAX_POLL_SEC})"))
            return
        self._batch_tr_poll_count = _pc + 1
```

### (d) 소요 시간 누적

`summary["elapsed_sec"] = round(time.time() - batch_start, 3)` **바로 다음 줄**에 추가:

```python

        self._batch_tr_poll_sec = getattr(self, "_batch_tr_poll_sec", 0.0) + summary["elapsed_sec"]
```

## A-5. GPT가 놓치기 쉬운 것 3가지

1. **조용히 자르지 말 것.** 기존 `BATCH_TR_MAX_CODES` 상한과 같은 방식으로 **거부 + ERROR 응답**이다.
   종목 수를 잘라서 부분 결과를 돌려주면 수집기가 구멍 난 1분봉을 정상으로 저장한다.
2. **부등호는 `not (x <= MAX)` 형태로.** 8/7에 확정한 프로젝트 규칙이다.
   `if x > MAX` 는 x 가 NaN 일 때 거짓이라 상한을 그냥 지나간다.
3. **초기화는 `poll_requests()` 안.** (b) 위치를 틀리면 예산이 영원히 리셋 안 되거나(=며칠 뒤 수집 정지),
   매 요청마다 리셋된다(=수리 효과 0).

# 작업 B — NaN 금액상한 형태 통일 (🟡 A가 끝난 뒤 별건으로)

## B-1. 정정 — 지금은 실제로 뚫리지 않는다

메모에는 "`broker_gateway_v1.py:2472,2475` NaN 이 시장가 금액상한을 우회"라고 적혀 있는데,
**재조사 결과 NaN 이 들어갈 경로가 없다.**

| `_est` 출처 | NaN 주입 가능? | 근거 |
|---|---|---|
| `self._micro_snapshot[code]["cur"]` | **불가** | 브로커가 키움 실시간에서 직접 채운다. `live_micro_snapshot.json` 은 **쓰기 전용**이고 디스크에서 되읽는 코드가 없다 (`:1446~1449`) |
| `GetMasterLastPrice(code)` | **불가** | 키움 OCX 반환 문자열. `float()` 이 NaN 이 되려면 문자열이 literally `"nan"` 이어야 한다 |
| `qty` · `price` | **불가** | `int(...)` 로 파싱한다 (`:2384~2385`). NaN 이면 예외로 걸러진다 |

**따라서 이 항목은 "실사고 봉합"이 아니라 "형태 통일(방어)"이다.** 우선순위를 A보다 낮게 둔 이유다.

## B-2. 그래도 고칠 값어치 — 비용 3줄

현재 구조는 두 갈래다.

```python
                if _est > 0 and qty * _est > _max_krw:        # :2472
                    _deny = (...)
                elif _est <= 0:                                # :2475
                    if qty <= 1:
                        logger.warning(...)
                    else:
                        _deny = (...)
```

`_est > 0` 과 `_est <= 0` 은 **둘 다 거짓이 되는 값(NaN)이 존재한다.**
그때는 어느 갈래도 안 타고 **아무 금액 검사 없이 통과**한다.
지금은 그 값이 못 들어오지만, 이 자리에 다른 값 출처가 붙는 순간 조용히 뚫린다.

## B-3. 고칠 내용

위 인용 블록(`if _est > 0 and ...` 부터 마지막 `_deny = (...)` 까지)을 아래로 **통째 교체**:

```python
                # ★[SEC-ORDERCAP-NAN 2026-08-10] 갈래를 "추정가가 있나"로 먼저 가른다.
                #   종전 `if _est > 0 ... elif _est <= 0` 은 둘 다 거짓인 값(NaN)에서
                #   아무 검사도 없이 통과했다. 지금은 NaN 주입 경로가 없지만
                #   값 출처가 하나 늘면 그때 조용히 뚫린다. 부등호는 뒤집어 쓴다(8/7 규칙).
                if not (_est > 0):          # NaN·0·음수 = 추정가 없음으로 취급
                    if qty <= 1:
                        logger.warning(
                            "[SEC-ORDERCAP] 시장가 code=%s 추정가 없음 — 1주 주문이라 통과(금액 유계)",
                            code)
                    else:
                        _deny = (f"시장가 추정가 없음 + 다수량 (qty={qty}) — "
                                 f"금액 검사 불가로 차단")
                elif not (qty * _est <= _max_krw):
                    _deny = (f"금액 상한 초과 (시장가 추정 qty*{_est:.0f}"
                             f"={qty * _est:.0f} > {_max_krw})")
```

> ⚠️ **분기 순서가 뒤집힌다.** "금액 초과" 갈래가 위에서 **아래로** 내려가고,
> "추정가 없음" 갈래가 아래에서 **위로** 올라온다. 여기서 실수하기 쉽다.
> 두 갈래의 **본문은 한 글자도 바꾸지 않는다** — 위치만 바뀐다.

### (선택) 같은 김에 형태 통일

`elif _max_krw > 0 and price > 0 and qty * price > _max_krw:` (`:2443`)
→ `elif _max_krw > 0 and price > 0 and not (qty * price <= _max_krw):`

지정가 경로다. `price` 가 `int` 라 역시 NaN 은 못 들어온다. 형태 통일 목적일 뿐이다.

## B-4. 검증 — 핵심은 "판정이 안 바뀌는 것"

```
[1] 아래 4가지 입력에서 판정이 수정 전과 100% 동일할 것
    · 추정가 있음 + 금액 상한 이내   → 통과
    · 추정가 있음 + 금액 상한 초과   → 차단 (_deny 문구까지 동일)
    · 추정가 없음(_est=0) + qty=1    → 통과 + [SEC-ORDERCAP] 경고 1줄
    · 추정가 없음(_est=0) + qty=2    → 차단

    🚨 새로운 차단이 하나라도 생기면 실패다. 현 체제는 전부 1주라 실전 영향은 0이어야 정상.

[2] _est = float("nan") 을 넣었을 때
    수정 전: _deny 가 None 으로 남는다(=통과)   ← 이걸 먼저 재현해서 보일 것
    수정 후: "시장가 추정가 없음" 갈래로 떨어진다

[3] pytest 11 failed / 558 passed 기준선 유지 (실패 이름까지 대조)
```

IPC 에 요청을 넣을 수 있는 권한(UserK)이면 **서명키도 그냥 읽어서 스스로 서명할 수 있고**,
애초에 `secrets.ps1` 을 열면 계좌번호가 바로 나온다.
**서명을 걸어도 실제로 막히는 상대가 없다.**

## 반면 부작용은 실재한다

정당한 호출자 2곳이 **BrokerClient 를 안 거치고 IPC json 을 직접 쓴다** = 자동 서명이 안 된다.

- `RUN\rt_sell_engine_v3_19.py:1404` — `_broker_request_se(...)` ← **매도엔진 계좌 조회**
- `RUN\kiwoom_buy_order_sender_v4_9.py:4421` — `_broker_request_bu(...)`

`PROTECTED_TYPES` 에 `ACCOUNT_INFO` 를 넣는 순간 둘 다 조용히 실패하고 OCX 직접조회로 넘어간다.
브로커 모드에서 OCX 가 없으면 **계좌번호가 빈 값 → 매도 불가**다.

8/11 아침은 이미 확인할 것이 3건(S01 3단계 수정 · 저장잠금 수리 · 복구그물 첫 실전) 예약돼 있다.
**매도 경로에 새 변수를 넣기에 최악의 타이밍이다.**

## 그래도 하게 될 경우의 순서 (지금은 아님)


**1·2·3 을 한 번에 시키면 매도가 멈춘다.**
