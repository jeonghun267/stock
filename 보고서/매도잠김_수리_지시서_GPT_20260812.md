# 작업 A — 시간청산은 재시도 상한을 면제한다 (🔴 최우선)

## A-1. 원칙

**하루를 넘기지 않기 위한 청산을 막으라고 있는 것이 아니다.**

# 작업 B — 매도 재무장(RECOVERY_SELL_REARM)을 공용코어에 이식 (🔴)

## B-1. 정답은 이미 S06에 있다 — 새로 설계하지 말 것

`strategy_06_crash_low_chase_v1.py:2130~2171` 을 그대로 읽고 공용코어의 대응 위치로 옮긴다.
**새 패턴을 만들지 말고 이 코드를 복사해 이름만 맞출 것.**

```python
        if actual_qty > 0:
            sell_exhausted = (
                int(position.get("sell_retries") or 0)
                >= self.config.max_sell_retries
                and bool(position.get("entry_at"))
            )
            if sell_exhausted:
                open_sell = self.broker.open_orders(code, buy=False)
                if open_sell is None:
                    return                                   # ← 브로커 진실 불명이면 안 건드린다
                if open_sell or available_qty <= 0:
                    self._event(
                        "RECOVERY_SELL_REARM_WAIT",
                        code=code,
                        reason=(f"open_sell={open_sell} available={available_qty}"),
                    )
                    return                                   # ← 미체결이 살아 있으면 중복 매도 금지
                position["qty"] = min(int(position.get("qty") or actual_qty), actual_qty)
                position["pending"] = None
                position["sell_retries"] = 0                 # ← 여기서만 초기화
                position["sell_recovery_cycle"] = (
                    int(position.get("sell_recovery_cycle") or 0) + 1
                )
                position["retry_after_epoch"] = (
                    time.time() + max(5.0, self.config.fill_wait_sec)
                )
                position["phase"] = "HOLD"
                self.state["last_error"] = ""
                self._event(
                    "RECOVERY_SELL_REARMED",
                    code=code,
                    quantity=position["qty"],
                    reason=("broker holdings present, available qty positive, "
                            "no open sell order"),
                )
                self._refresh_recovery_blocked()
                return
```

## B-2. 이 코드가 안전한 이유 — 세 개의 자물쇠

| 자물쇠 | 무엇을 막나 |
|---|---|
| `open_sell is None` → `return` | **브로커 조회 실패 시 아무것도 안 한다.** 오늘 사고의 1단이 바로 이 상황 |
| `open_sell` 있으면 대기 | **미체결 매도가 살아 있는데 또 던지는 것**을 막는다 (중복 매도 = 없는 주식 매도) |
| `available_qty <= 0` 이면 대기 | 결제 미도래·이미 묶인 수량을 팔려다 거부되는 것을 막는다 |

**이 세 줄 중 하나라도 빼면 중복 매도 사고가 난다. 전부 그대로 옮길 것.**

## B-3. 공용코어에서 넣을 위치

`RECOVERY_HOLD_RESUMED` 를 내보내는 블록(현재 2307~2311줄) **바로 앞**이다.
재무장 조건에 맞으면 재무장하고 `return`, 아니면 기존 `RECOVERY_HOLD_RESUMED` 로 떨어지게 한다.

**주의 — 필드명 실측 결과(그대로 따를 것)**

| 필드 | 공용코어 | S06 | 지시 |
|---|---|---|---|
| `entry_at` | **있음** (`:1360` 초기화 · `:1488` 진입 시 기록) | 있음 | 그대로 써도 된다 |
| `hold_state` | 있음 — **주변 복구 블록이 이걸로 보유를 판정한다**(`:2307`) | 없음 | **재무장 조건은 이쪽에 맞출 것** |
| `entry_no` | **없음** | 있음 | **멱등키에서 이 조각은 빼라**(A-4 참조) |

즉 `sell_exhausted` 판정의 `and bool(position.get("entry_at"))` 은 공용코어에서도 동작하지만,
**바로 아래 기존 블록이 `hold_state` 로 판정하므로 둘이 어긋나면 재무장과 HOLD 복귀가 따로 논다.**
**주변 블록과 같은 기준(`hold_state`)으로 통일할 것.** 없는 필드를 참조하면 조건이 항상 거짓이 되어
아무 일도 일어나지 않고, 그건 로그에도 안 남는다.

4. `sell_recovery_cycle=3` → 재무장 **안 됨**
5. 재무장 직후 `retry_after_epoch` 때문에 **즉시 재주문이 안 나가는지**(연타 방지)
6. **오늘 사고 재현**: `_start_sell` 3회 TIMEOUT → EXHAUSTED → 재무장 → 매도 성공까지 한 흐름으로

---

# 작업 C — SELL_RETRY_EXHAUSTED 이벤트 쿨다운 (🟡 마지막에)

오늘 1시간 38분 동안 **347회** 찍혔다. 중계·로그·이벤트 저널을 전부 오염시킨다.

`_start_sell` 의 차단 분기에서, **같은 종목에 대해 60초 안에는 이벤트를 다시 내보내지 않는다.**
상태 전이(`phase`·`last_error`)는 그대로 두고 **`self._event(...)` 호출만** 건너뛴다.

```python
EXHAUSTED_EVENT_COOLDOWN_SEC = 60.0
```

**[검증]** 같은 포지션에 10초 간격으로 10번 부르면 이벤트가 **1~2회만** 나오는가. 상태는 그대로 `RECOVERY_BLOCKED` 인가.

# 작업 D — 브로커 20초 주기 TIMEOUT (⚪ 조사만, 코드 수정 금지)

## D-1. 관측 사실

```
2026-08-12 08:44:05 부터  [HFIX-v2] TIMEOUT recovery wait 0.5s (non-blocking)
                          RES <uuid> status=TIMEOUT
08:35~08:55 집계          OK 257 / TIMEOUT 56 / ERROR 0 / 인증거부 0
간격                      약 20~21초 규칙적 (08:53:47 · 08:54:08 · 08:54:29 …)
```

어제(8/11)도 09:00~09:21 동안 `BALANCE_UNAVAILABLE:TR response timeout (20s)` 가 반복됐다.

## D-2. 조사할 것 — **답만 가져올 것. 고치지 말 것.**

1. TIMEOUT 나는 요청의 **`type` 과 `tr_code` 가 무엇인가** (특정 TR 하나인가, 무차별인가)
2. **20초 주기의 정체** — 어떤 타임아웃 상수가 20초인가, 누가 20초마다 재요청하는가
3. **호출자가 누구인가** — `caller=` 필드로 특정. BrokerClient 경유인가, IPC json 직접인가
4. 8/11 20:03 게이트웨이 변경(`_wire_tr_rqname` 신설)과 **시점 상관이 있는가**
   → 8/10 이전 로그와 TIMEOUT 발생률을 비교할 것

## D-3. 왜 고치지 말라는가

오늘 장중 `broker_gateway_v1.py` 가 **백업 없이 이미 두 번 손대졌다**(8/11 20:03, 8/12 12:38).
원인 미규명 상태에서 세 번째로 손대면 **무엇이 무엇을 고쳤는지 영원히 못 가린다.**
작업 A·B는 증상을 확실히 막아준다. D는 그 다음 판에서 근거를 갖고 한다.
