# S01 최소수정 최종 설계도

작성일: 2026-08-31  
상태: 구현 및 필수검사 보강 완료

## 1. 목적과 범위

이번 작업은 아래 두 가지 변경과 한 가지 읽기 전용 확인만 한다.

1. S01의 `ROCKET`·`PULLBACK` 레인마다 하루 서로 다른 진입 종목을 최대 3개로 제한한다.
2. S01 주문 생명주기 감사에 진입 추격폭과 체결 미끄러짐을 실제 값으로 기록한다.
3. 현재 사용 중인 `COMMON_FLOW_DEFENSE_EXIT`의 설정과 작동 근거만 읽기 전용으로 진단한다. 값은 바꾸지 않는다.

과거 엔진 로그에서 계산한 손익·승률 수치는 브로커 원장 전체 검증을 통과하지 않았으므로 이 설계의 실전 성과 근거로 사용하지 않는다.

## 2. 절대 변경 금지

- 공용 `broker_client.py` 및 공용 레짐 관문
- 매수 신호 조건, 3초 확인, 60초 진입 간격
- 손절·상승보유·강제청산·`PROFIT_TRAIL`·`COMMON_FLOW_DEFENSE_EXIT` 값
- 총 슬롯 6개, 레인별 동시 슬롯 3개, 수량 1주
- S02~S06 전략 파일과 런처
- S01 신규매수 LIVE/SHADOW 상태

## 3. 작업 A — 레인별 일일 서로 다른 종목 3개

### 수정 파일

`RUN\strategy_01_rotation_engine_v2.py` 한 파일

### 현재 문제

현재 `lane_active`는 `active_positions`만 세기 때문에 매도 후 같은 레인의 동시 슬롯이 다시 열린다. 기존 동시보유 제한은 유지하고 일일 서로 다른 종목 제한을 추가한다.

### 상태 형식

`_blank_state()`에 다음 상태를 추가한다.

```python
"entered_codes_by_lane": {
    "ROCKET": [],
    "PULLBACK": [],
},
```

- 목록에는 6자리 종목코드만 저장한다.
- 같은 코드의 재진입은 같은 레인에서 한 번만 센다.
- 같은 코드가 서로 다른 레인으로 실제 진입했다면 각 레인에서 한 번씩 센다.
- 매도·주문실패 때 목록에서 제거하지 않는다.
- 날짜가 바뀌어 `_blank_state()`가 만들어질 때만 초기화한다.

### 재기동·기존 상태 호환

`_load_state()`는 단순 `setdefault`만 하지 않는다.

1. 저장된 `entered_codes_by_lane`를 읽어 6자리 코드로 정규화한다.
2. 배포 전 형식처럼 이 키가 없거나 불완전하면 같은 날의 `positions`와 `history`에서 `entry_at`과 `entry_stage`가 있는 `ROCKET`·`PULLBACK` 진입을 합쳐 복원한다.
3. 중복을 제거하고 정렬된 목록으로 상태에 다시 넣는다.

이 복원 절차가 없으면 장중 재기동 때 이미 사용한 레인 자리가 다시 열리므로 반드시 포함한다.

### 진입 관문

기존 `lane_active` 판정을 그대로 유지하고 같은 위치에 `lane_daily`를 추가한다.

```python
lane_active = 현재 보유·주문 중 같은 레인 수
lane_daily = entered_codes_by_lane[entry_stage]의 서로 다른 코드 수

if lane_active >= lane_limit:
    기존 "{entry_stage}_SLOT_LIMIT_3"
elif code not in lane_daily_codes and lane_daily >= lane_limit:
    신규 "{entry_stage}_DAILY_CODE_LIMIT_3"
```

- 기존 코드의 허용된 재진입은 일일 서로 다른 종목 수를 늘리지 않는다.
- 신규 일일 제한 차단도 기존 레인 차단과 같이 주문·자금 예약 전에 실행한다.
- 기존 신호 소비 방식은 바꾸지 않는다.

### 체결확정 반영

`_confirm_entry()`에서 `entry_stage`가 `ROCKET` 또는 `PULLBACK`이고 체결이 확인된 경우 해당 레인 목록에 코드를 한 번만 추가한다.

- 주문 제출만으로 세지 않는다.
- `BUY_FILL_CONFIRMED` 또는 기존 order-zero 체결확정 경로에서만 센다.
- 추가매수의 조기 `return`보다 먼저 공통 처리를 적용해 경로 누락을 막는다.

### 집중검사

1. 같은 레인에서 서로 다른 코드 3개까지 허용한다.
2. 같은 레인의 네 번째 신규 코드는 `*_DAILY_CODE_LIMIT_3`으로 차단한다.
3. 매도 후에도 네 번째 신규 코드는 차단한다.
4. 같은 코드 재진입은 일일 코드 수를 늘리지 않는다.
5. 다른 레인은 독립적으로 3개까지 허용한다.
6. 저장 후 재기동해도 레인 목록이 유지된다.
7. 구형 상태파일은 `positions`·`history`에서 당일 레인을 복원한다.
8. 다음 거래일의 빈 상태에서는 두 목록이 초기화된다.

## 4. 작업 B — 진입 텔레메트리 복구

### 수정 위치

같은 파일의 `_order_lifecycle()` 기록 생성부만 수정한다. 주문 선택·차단 경로에는 코드를 넣지 않는다.

### 값의 정확한 정의

```python
signal_snapshot = position.get("signal_snapshot") or {}
signal_emitted_price = number(
    signal_snapshot.get("signal_emitted_price")
    or signal_snapshot.get("price")
)
arrival_price = number(position.get("signal_price"))

arrival_chase_bps = (
    (arrival_price / signal_emitted_price - 1.0) * 10000.0
    if signal_emitted_price > 0 and arrival_price > 0 else None
)
fill_slippage_bps = (
    (number(fill_price) / arrival_price - 1.0) * 10000.0
    if number(fill_price) > 0 and arrival_price > 0 else None
)
```

감사 레코드에 다음 네 필드를 추가한다.

- `signal_emitted_price`
- `arrival_price`
- `arrival_chase_bps` — 값이 있으면 소수점 넷째 자리 반올림
- `fill_slippage_bps` — 값이 있으면 소수점 넷째 자리 반올림

`position["signal_price"]`는 현재 코드에서 주문 직전 스냅샷 가격이므로 이름을 바꾸지 않는다. `fill_source`도 그대로 기록해 브로커 체결원장과 잔고 재조정 값을 구분한다.

### 금지사항

- S02의 `25bps` 문턱을 가져오지 않는다.
- `ARRIVAL_PRICE_COLLAR` 또는 다른 매수 차단을 추가하지 않는다.
- 값이 없을 때 0으로 채우지 않는다.
- 감사 스키마 이름과 기존 필드를 변경하지 않는다.

### 집중검사

1. 유효한 세 가격으로 두 bps 계산이 정확하다.
2. 발행가·도착가·체결가가 없거나 0이면 해당 계산값은 `None`이다.
3. `BUY_FILL_CONFIRMED`에는 유효한 체결가가 있을 때 네 값이 기록된다.
4. 주문 제출 전후의 매수 허용·차단 결과와 주문 수는 변경 전과 같다.
5. `record_sha256`는 새 네 필드를 포함한 레코드로 계산된다.

## 5. 작업 C — COMMON_FLOW_DEFENSE_EXIT 읽기 전용 진단

- 현재 S01 프로파일은 `profit_trail=False`, `trail_steps=None`이므로 `PROFIT_TRAIL`은 진단 대상에서 제외한다.
- 현재 사용 중인 `COMMON_FLOW_DEFENSE_EXIT`의 발동점수·확인시간·입력자료·매도 우선순위만 확인한다.
- `strategy_common_hold_sell_v1.py`, 프로파일, 매도조건과 숫자는 이번 작업에서 수정하지 않는다.
- 과거 청산 성과 숫자는 브로커 체결원장과 연결된 보고서가 `trading_report_truth_gate_v1.py`를 통과한 경우에만 인용한다.
- 변경 필요성이 확인돼도 공용값을 직접 바꾸지 않고 S01 전용 영향범위와 재생검증을 별도 설계한 뒤 승인을 받는다.

## 6. 작업 순서

1. 15:30 이후 실전 파일의 해시와 수정 전 백업을 남긴다.
2. 작업 A만 반영하고 컴파일·집중검사·S01 회귀검사를 끝낸다.
3. A가 통과한 상태에서 별도 변경 묶음으로 작업 B만 반영하고 같은 검사를 다시 한다.
4. 공용 부모 파일 변경 영향 때문에 관련 기준선 검사를 한 번 실행한다. 새 실패가 있으면 원본 모듈과 대조해 A·B 귀속 여부만 판단한다.
5. `approval_manifest_writer_v1.py`의 CAS 경로로 명부의 `common`과 `S01` 중복 항목을 모두 새 해시로 갱신한다.
6. `live_owner_approval_guard_v1.py`로 S01·S02·S03·S06 기동 해시를 확인한다.
7. 프로세스 재시작과 실계좌 주문은 실행하지 않는다. 다음 정규 기동부터 반영한다.

## 7. 완료 조건

- diff가 작업 A의 상태·관문·체결반영과 작업 B의 감사 필드에만 한정된다.
- S01 회귀검사가 전부 통과한다.
- 관련 기준선에 A·B 귀속 새 실패가 없다.
- 명부 `common`·`S01`의 파일 해시가 실제 파일과 일치한다.
- S01·S02·S03·S06 승인 해시 검사가 통과한다.
- 매수조건·매도조건·수량·총슬롯·기존 동시 레인슬롯은 변경되지 않는다.
- 주문 거절·타임아웃은 레인 일일 사용내역을 증가시키지 않는다.
- 거래일이 바뀌면 레인 일일 사용내역이 초기화된다.

## 8. 표본 충족 후 분석 계약

분석은 **10거래일 이상**과 **유효표본 30건 이상**을 모두 충족한 뒤 시작한다. 둘 중 하나가 늦으면 늦은 조건까지 기다린다.

유효표본은 다음 조건을 모두 만족해야 한다.

- 이벤트가 `BUY_FILL_CONFIRMED`이다.
- `signal_emitted_price`, `arrival_price`, `fill_price`가 모두 0보다 크다.
- `arrival_chase_bps`, `fill_slippage_bps`가 `None`이 아니다.
- `order_no`로 브로커 체결원장과 연결되고 `fill_source`가 `BROKER_FILL_JOURNAL`로 확인된다.

분석 절차:

- 감사행을 `signal_id`·`order_no`·종목·거래일로 브로커 체결원장과 연결한다.
- 체결시각·체결가·손익을 인용하기 전 `RUN\trading_report_truth_gate_v1.py`를 통과한다.
- 완전한 진입·청산 경로가 증명되지 않은 재생에서는 매수 허용·차단 판단만 보고하고 손익은 계산하지 않는다.
- 두 표본조건과 진실성 검사를 충족하기 전에는 `arrival_chase_bps` 문턱이나 신규 매수 차단조건을 추가하지 않는다.

## 9. 롤백

수정 전 백업을 원위치에 복원하고, CAS 명부의 `common`·`S01` 두 해시를 복원 파일 해시로 함께 되돌린다. 작업 A와 B는 별도 백업·검증 단위로 유지해 각각 독립적으로 되돌릴 수 있게 한다.
