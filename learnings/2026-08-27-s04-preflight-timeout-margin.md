# 2026-08-27 S04 사전점검의 8초 타임아웃은 "가끔 나는 일"이 아니라 마진 0.02초짜리 시한폭탄이었다

## 접근법
1. 오늘 로그에서 `STRATEGY04_PREFLIGHT_FAIL TimeoutExpired ... after 8 seconds` 1건을 발견했다.
2. "가끔 나는 일"로 넘기지 않고 **왜 8초를 넘겼는지**를 코드로 확인했다 →
   `REQUIRED_TASKS` 8개를 `_task_enabled(name)` 로 **하나씩** 조회, 즉 PowerShell 프로세스 8개.
   (코드 주석도 "여러 PowerShell subprocess 때문에 수 초가 걸린다"고 이미 인정하고 있었다.)
3. 고치기 전에 **옛 방식의 실제 소요를 쟀다**: 한가한 21시에 **7.98초**. 타임아웃 8초와 마진 0.02초.
   → 아침 혼잡에는 사실상 확정 실패. 오늘 FAIL 은 우연이 아니었다.
4. 소비 쪽 영향도 확인했다: LIVE 런처 deadline 은 12:00 이고 0.5초마다 재확인한다
   → **지연 자체는 치명적이지 않고, 09:00 한 번 실패하면 아무도 다시 안 부르는 것**이 진짜 위험이었다.
5. 호출을 `Get-ScheduledTask -TaskName @(...)` **1회 배치**로 바꾸고 timeout 25 + 재시도 1회.
6. 신구 결과를 8개 전부 대조(완전 일치)하고, 없는 태스크가 여전히 False 인지(fail-closed) 확인했다.

## 하지 않은 것 + 이유
- 타임아웃만 8→20 으로 올리지 **않았다**. 이유: 원인은 시간이 아니라 **프로세스 8개**다.
  숫자만 올리면 아침에 다시 그 문턱에 붙는다. 호출 수를 줄이는 게 근본이다.
- 타임아웃을 fail-open(확인 불가 시 통과)으로 바꾸지 **않았다**. 이유: 이 검사는 워치독 활성 확인이라
  안전장치다. 통과시키면 사전점검의 의미가 사라진다. 끝내 확인 불가면 여전히 FAIL 시킨다.
- `schtasks.exe` 로 갈아타지 **않았다**. 이유: 출력 포맷이 로케일(한글)에 좌우된다.
  같은 cmdlet 을 유지하면 결과 동치를 대조로 증명할 수 있다.
- 전체 preflight 를 `--approve` 로 돌려보지 **않았다**. 이유: 오늘 날짜 승인을 실제로 쓴다.
  인자 없는 read-only 로 돌리고 플래그 mtime 무변경을 확인했다.
- 앞선 검사(`PREFLIGHT_CONTEXT_SELFTEST:STALE`)를 고치지 **않았다**. 이유: 밤이라 stale 인 게 정상이고
  범위 밖이다. 그 한 검사만 우회해 **내 수정 구간까지 도달하는지**만 확인했다.

## 재사용 규칙
타임아웃 실패를 고칠 때는 한도를 올리기 전에 **평상시 실제 소요를 재라** —
한도에 붙어 있으면 원인은 시간이 아니라 호출 구조다.
