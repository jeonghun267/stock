# 세 전략 공동 실전준비에서 드러난 실패폐쇄 경계

## 문제

S01·S02·S03을 서로 독립된 프로세스로 실행하면서도 다음 거래일에만 함께 자동 활성화해야 했다. 각 전략의 OFF/승인 확인만으로는 프로세스 간 공용 슬롯 경쟁, 예약작업 상태 오판, 한 전략만 부분 활성화되는 위험을 막을 수 없었다.

## 해결 접근

1. 세 전략의 거래일 가드를 먼저 만들고 상태·복구대기·기존 골짜기·공용 슬롯·계좌 잔고·전체 미체결·당일 후보자료·정확 최우선호가를 하나의 사전점검에서 검사했다.
2. 모든 조건이 통과할 때만 세 승인파일 생성과 세 OFF 해제를 한 묶음으로 수행하고, 중간 실패 시 모두 OFF로 복구했다.
3. LIVE 작업은 당일 공통 사전점검의 `PASS` 기록과 전략별 활성화 명단을 다시 확인한 뒤에만 엔진을 import하도록 분리했다.
4. 공용 슬롯의 read-check-write 구간을 Windows 프로세스 파일 잠금으로 감싸 동일 종목 동시 진입을 원자적으로 차단했다.
5. `schtasks /Query /XML`의 실제 UTF-8 바이트와 잘못된 UTF-16 선언을 분리 처리해 예약작업을 거짓 비활성으로 판단하던 문제를 고쳤다.

## 시도와 검증

- 시도 1: 독립 Python으로 LIVE 게이트 실행 → 모듈 경로 누락으로 실패.
- 수정: `RUN` 경로를 명시적으로 `sys.path`에 추가 → 격리 실행 통과.
- 시도 2: 예약작업 XML을 바이트 그대로 파싱 → 인코딩 선언 충돌로 실패.
- 수정: BOM을 확인하고 실제 바이트를 먼저 문자열로 디코딩 → 현재 예약작업과 회귀 케이스 통과.
- 최종: S01 31개, S02 5개, S03 15개, 공통·후보·사전점검·동시성 40개로 총 91개 PASS. 일요일 수동 예약실행은 세 전략 모두 OFF·승인 없음·주문 시도 0을 유지했다.

## 채택하지 않은 방법

- 전략별 사전점검과 개별 승인: 한 전략만 활성화되는 부분 성공을 만들 수 있어 제외했다.
- 원자적 파일 교체만 사용: 파일 손상은 막지만 두 프로세스의 read-check-write 경쟁은 막지 못해 제외했다.
- 오늘 계좌 성공을 내일도 유효하다고 간주: 실계좌·미체결·호가 상태는 거래일마다 변하므로 제외했다.

## 재사용 규칙

- 여러 주문 프로세스를 같은 날 열 때는 승인도 개별 토글이 아니라 일일 공동 임대(lease)로 취급한다.
- 파일 기반 공유 상태의 정합성과 상호배제는 별개다. 원자적 쓰기와 프로세스 잠금을 함께 검증한다.
- 외부 명령 XML은 선언만 믿지 말고 실제 바이트 인코딩을 먼저 확인한다.
- 자동 실전은 사전점검이 실패하면 복구를 시도해 억지로 열지 않고 전 전략을 닫는 방향으로 실패해야 한다.
