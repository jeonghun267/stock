# [2026-08-26] 로그가 13:17에 끊긴 것을 "전략 사망"으로 오판했다 — 실제로는 15:25 정상 종료

## 문제 한 줄
S06(급락저점추격) 로그가 13:17:09에서 멈춰 있어 "오후 2시간 13분간 죽어 있었다"고
사전점검에서 보고했으나, 프로세스는 15:25까지 정상 가동 후 정상 종료한 상태였다.

## 접근법
1. 태스크 종료 코드 확인 → `LastTaskResult=0`(정상 종료). 예외사(1)가 아님을 먼저 확인.
2. 코드의 종료 경로를 전수 grep → `raise SystemExit(main())` 단 1개.
   run 루프의 return 조건 3개(주말 / 16:00 / `process_end`)만 존재.
3. `process_end` 실값 확인 → `day_time(15, 25)` 하드코딩, 런처 .cmd에 덮어쓰는 환경변수 없음.
   ⇒ **13:17 종료를 설명하는 정상 경로가 하나도 없다** = 전제가 틀렸다는 신호.
4. 프로세스 생존을 로그가 아닌 **산출물 mtime**으로 재측정:
   - `data\strategy_06_crash_low_chase_state_v1.json` → **15:25** (= process_end와 정확히 일치)
   - `strategy_06_signals_20260826.csv` → 13:29 (로그보다 12분 늦음)
5. signals 마지막 줄로 확정:
   `13:17:09 CHASE_TRIGGER 스피어(347700)` → 관찰 720초 → `13:29:10 OBSERVE_TIMEOUT`.
   매수 조건 미충족으로 관찰 종료. 이후 15:25까지 -8% 급락 종목 0건 ⇒ **찍을 이벤트가 없었을 뿐.**

## 하지 않은 것 + 이유
- **워치독·taskkill 이력 추적을 하지 않음.** 이유: 3단계에서 "13:17 종료를 설명하는 정상 경로가
  없다"가 나온 시점에 이미 전제(=죽었다)를 의심해야 했다. 외부 살해자를 찾는 것은
  틀린 전제 위에 수사를 얹는 것이라 비용만 늘어난다.
- **로그의 `PermissionError`/`Traceback`을 오늘 원인으로 채택하지 않음.** 이유: 행번호가
  1260~1498인데 오늘 이벤트는 1617행 이후 — **과거 날짜 기록**이었다.
  누적 로그에서 grep 결과를 쓸 때는 행번호로 시간축을 먼저 맞춰야 한다.
- **과거 날짜 파일들이 전부 13~14시에 끝나는 것을 "만성 사망"으로 결론내지 않음.**
  이유: 같은 착시의 반복일 뿐이었다(8/24 13:25, 8/25 14:22 등 = 그날의 마지막 이벤트 시각).

## 재사용 규칙
**이벤트 기반 로그의 침묵을 프로세스 사망의 증거로 쓰지 마라.**
생존은 로그가 아니라 **주기적으로 갱신되는 산출물의 mtime**(상태 JSON)으로 판정하고,
"멈췄다"고 말하기 전에 **코드의 종료 경로가 그 시각을 설명하는지** 먼저 대조하라.
설명하는 경로가 하나도 없으면 — 고장이 아니라 **내 전제가 틀린 것**이다.
