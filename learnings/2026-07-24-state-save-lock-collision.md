## 접근법
1. 로그에서 PermissionError 발생 시각을 전부 뽑아 패턴 확인 → 전부 매분 :00~:01초에 몰림
2. 그 초에 도는 프로세스를 태스크 목록에서 대조 → 중계(BROADCAST)가 1분 주기로 state json을 읽음
3. 반증 시도: 중계가 범인이면 중계 종료 후엔 저장이 성공해야 함 → 중계 종료 15:30 직후 15:31에 최종 저장 성공 (파일 mtime으로 확인)
4. 메커니즘 확정: Windows에서 os.replace는 대상 파일을 다른 프로세스가 share-delete 없이 열어두면 WinError 5 — 스크래치패드에서 리더 스레드로 재현해 재시도 2차에 성공함을 실증
5. 수술: 호출처(_save_state) 한 곳뿐임을 grep으로 확인 후, 그 자리에서 3회 재시도+최종 삼키기 — 유틸(atomic_json_write)의 계약은 건드리지 않음

## 하지 않은 것 + 이유
- 중계 쪽(읽기)을 복사 후 읽기로 고치지 않음. 이유: 엔진 쪽 재시도가 근본(앞으로 state를 읽는 리더가 늘어도 안전)이고, 개장 전 수정 범위를 1곳으로 최소화. 중계 수정은 WARNING이 잦을 때의 2차 카드로 보류
- 트레이스백에 찍힌 줄번호(2481/2320/448)로 코드를 바로 열지 않음. 이유: 트레이스백 본문에 주석·독스트링이 찍혀 있었음 = 장중에 파일이 편집돼 줄번호가 이미 어긋난 상태. def를 grep으로 다시 찾는 게 정답이었음
- PowerShell `Set-Content -Encoding utf8`로 해시 기준선을 쓰고 끝내지 않음. 이유: PS 5.1은 BOM을 붙이는데 배선점검이 `read_text().split()[0]`으로 읽어서 첫 토큰이 오염됨 → BOM 없는 WriteAllText로 재작성하고 배선점검과 동일 로직으로 대조까지 실행
