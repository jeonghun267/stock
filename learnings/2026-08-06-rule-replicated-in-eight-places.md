# [2026-08-06] 설계 규칙 하나(-8% 인계)를 없애려니 같은 규칙이 8곳에 복제돼 있었다 — 한 곳만 고치면 다른 곳이 조용히 다 버린다

## 접근법
1. 규칙을 바꾸기 전에 "이 규칙을 아는 코드"를 전부 색출 (상수명 grep 이 아니라 **동작 단위**로:
   숫자 -8 을 아는 곳, 시간창 09:20 을 아는 곳, 레인 이름으로 갈리는 곳을 각각 따로 찾음)
2. 신호가 태어나서 주문이 되기까지의 **경로 순서대로** 차단 지점을 나열
   (검출기 → 레인 라우팅 → 계약 검증 → 회전엔진 재검산 → 매도 프로파일)
3. 차단 지점마다 "여기만 안 고치면 어떤 증상이 나나"를 먼저 적음
   (예: 계약 시간창을 빼먹으면 → 신호기는 쫓는데 신호가 전부 조용히 버려짐 = 관측 불가 실패)
4. 전부 고친 뒤 실자료 재생으로 **끝단 결과**(매수가 실제로 나오나)를 확인
5. 낡은 규칙을 잠그던 시험 3건은 삭제가 아니라 **새 규칙 잠금으로 교체**

## 하지 않은 것 + 이유
- **상수(OPEN_HANDOFF_DROP_PCT) 삭제는 하지 않음.** 이유: 설정 검증식(handoff < arm < 0)과
  낡은 백업들이 참조한다. 판정에서만 빼고 상수는 "은퇴" 주석으로 남기는 쪽이 diff 가 작다.
- **grep 한 번으로 끝냈다고 믿지 않음.** 이유: 같은 규칙이 상수 참조(-8%), 시간 비교(09:20),
  문자열(레인 이름), 파생 규칙(매도 프로파일 09:50)의 **네 가지 다른 얼굴**로 존재했다.
  상수명 grep 은 그중 하나만 잡는다. 실제로 시간창(09:02~09:20)은 -8 과 무관한 코드였다.
- **시험 개수만 보고 넘어가지 않음.** 이유: A/B 에서 12번째 실패가 새로 떴는데, 이름을 보니
  "표기가 시각보다 우선" 규칙을 잠그던 시험 — 새 설계가 그 규칙 자체를 뒤집는 것이었다.
  개수만 봤으면 "원래 실패하던 무리"에 섞여 넘어갔을 것(8/5 교훈 재확인).

## 재사용 규칙
설계 규칙 하나를 바꿀 때는 "그 규칙을 아는 코드"를 신호 경로 순서대로 전부 나열하고,
지점마다 "여기만 빼먹으면 나는 증상"을 먼저 적어라 — 조용히 버려지는 지점이 꼭 하나는 있다.
