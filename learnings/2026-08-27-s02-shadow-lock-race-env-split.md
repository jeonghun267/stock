# 2026-08-27 그림자A가 실전 S02 신호기와 같은 싱글톤 잠금을 두고 09:00에 경주해 실전을 41분 죽였다

## 접근법
1. "B·C 는 사본이라 무관"이라는 **기존 서술을 먼저 검증**했다 → 사본이라서가 아니라
   **잠금 도입 전 옛 버전(77~78KB vs 실전 124KB)** 이라 무관했던 것이었다(정정).
2. 실전 cmd 와 그림자A cmd 의 env 를 대조해 잠금 경로만 공유(하드코딩)임을 확인했다.
3. 선택지 2개의 **장기 열화**를 비교했다: 사본 분리는 실전이 바뀌면 낡아 그림자가
   "문턱 차이"가 아니라 "옛 코드 차이"를 재게 된다 → env 분리를 추천하고 승인받았다.
4. 실전 1줄(`lock_path` 하드코딩 → `os.environ.get("S02_LOCK_PATH", 기존경로)`)
   + 그림자A cmd 1줄(`set S02_LOCK_PATH=...`). cmd 는 CRLF/ASCII 를 바이트로 확인.
5. 1차 검증(두 프로세스 동시 생존)은 **FAIL** — 마감 후엔 신호기가 한 사이클 돌고 즉시 끝나
   둘 다 0개 생존. 판정 불능.
6. 방법을 바꿨다: **바깥에서 잠금 파일을 `msvcrt.locking` 으로 붙잡은 채 스크립트를 돌리고
   산출물(S02_OUTPUT) 유무로 판정** → 3/3 PASS.
7. 같은 방식으로 실전 회귀(env 미설정 → 기본 잠금)도 2/2 PASS 로 확인했다.
8. pytest 실패 9건은 백업본으로 **되돌려 기준선을 실측**해 동일함을 확인하고 즉시 복원(해시 대조).

## 하지 않은 것 + 이유
- 사본 분리(B·C 방식)를 택하지 **않았다**. 이유: 그림자A의 목적이 "실전과 같은 코드 + 다른 문턱"인데
  사본은 시간이 지나면 그 목적을 조용히 무너뜨린다. B·C 가 이미 그 상태다.
- 잠금 파일 **mtime 으로 판정하지 않았다**. 이유: `open("a+")` 는 내용을 안 바꾸면 mtime 을 갱신하지
  않아 위음성이 난다(실제로 1회 오판할 뻔했다).
- 실전 env 로 스크립트를 돌려보지 **않았다**. 이유: 실전 산출물 `strategy_02_low_buy_signal_v1.json`
  을 덮어쓴다. 출력·이벤트 env 를 임시 폴더로 돌려 격리한 뒤에만 실행했다.
- 잠금 실패 시 stderr 한 줄 남기는 개선을 **하지 않았다**. 이유: 요청 범위 밖.
  조용사 진단을 어렵게 하는 설계라 별건 안건으로만 남겼다.
- 그림자 B·C·실전 cmd·태스크 시각을 **건드리지 않았다**. 이유: 지시 범위가 그림자A 수리였다.
