# [2026-08-07 밤] 내가 만든 상한 검사를 NaN 하나가 지나갔다 — 다른 모델에 검사를 맡겨서 찾았다

## 접근법
1. 실계좌 코드를 밤에 고쳤으니 코드 검사를 하기로 했는데, **오늘 그 코드를 쓴 게 나(페이블 5)** 라는 점을
   먼저 짚었다. 같은 모델이 자기 코드를 보면 같은 사각지대를 두 번 본다
2. 그래서 나눴다 — **보안 검사는 오퍼스 5**(다른 눈), **정확성·회귀 검사는 나**
3. 오퍼스 5가 낸 지적을 믿지 않고 셋 다 직접 재현했다:
   `float("nan") > 120.0` → False 확인 · 경로 조립 실측 `C:\PROOF.json` · 해시 16건 직접 대조
4. 고친 뒤 **변조 시험**으로 잠금이 실제로 잡는지 확인(고치기 전 상태로 되돌려 FAIL 나는지)

## 하지 않은 것 + 이유
- **오퍼스 5의 보고를 그대로 옮겨 적지 않았다.** 이유: 검사관도 틀릴 수 있다.
  실제로 내 코드 검사에서 내가 "재기동 시"라고 쓴 진단이 부정확했던 전례가 같은 날 있었다.
- **BATCH_TR 폴당 누적 상한은 고치지 않았다.** 이유: 한 번에 하나씩(I항). 지적된 4건이
  다 검증된 뒤 별건으로 본다.
- **`_is_blanket_real_remove` 를 지우지 않았다.** 이유: 진단용으로는 쓸모가 있고, 지우면
  기존 시험 2건이 의미를 잃는다. 대신 "다시 관문으로 쓰이면 FAIL"을 ast 로 잠갔다.

## 재사용 규칙
상한·문턱 검사는 `if x > MAX` 가 아니라 **`if not (x <= MAX)`** 로 쓰라 —
NaN 은 모든 부등호 비교에서 거짓이라 앞의 형태는 이상값을 그냥 통과시킨다.

## 곁들여 배운 것
- **계약서·잠금 검사는 문자열 검색이 아니라 ast 로.** 문자열 검색은 주석을 코드로 착각한다
  (실제 배선을 지우고 주석에만 남겨도 PASS 였다). 같은 파일의 8/5 검사는 이미 이 교훈을
  주석으로 적어 뒀는데 내가 새로 만든 검사만 그걸 어겼다 — **기존 코드의 주석을 먼저 읽어라.**
- **검사자를 분리하면 실제로 다른 것이 나온다.** 친구님 규칙 K항("검증자는 액션과 분리")이
  모델 선택에도 그대로 적용된다.
